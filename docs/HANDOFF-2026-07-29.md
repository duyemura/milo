## Known intake gaps (NOT blocking; for later, surfaced by the live run)
- **Fonts fall back to `Inter/Inter`** — brand.ts uses static-regex CSS font detection and missed Buckhead's real Webflow faces. `apps/studio/src/fonts.mjs` already has robust Playwright computed-style font capture that intake should reuse. **Highest-leverage "feels like them" fix.**
- **Asset download not wired in the orchestrator** — `gym.json` images hot-link to the gym's CDN instead of local `/assets/`. `downloadAsset()` exists in `crawl.ts` but `intake.ts` doesn't call it. Matters for hermetic builds.
- **Crawl prioritization** is nav/keyword-based — misses non-nav-driven sites (Shopify `/pages/`+`/collections/`; and on Buckhead, 6 coach bios crowded out programs/pricing until we raised `--max-pages` to 25). Consider per-archetype caps / Shopify-aware rules.

## THE OPEN DECISION — what is `generate`? (resume here)

We were in `superpowers:brainstorming` for Generate. The tension: **intake already shortcuts crawl → `gym.json` in one LLM synthesis, but the architecture wants docs = truth, site = a re-runnable projection.** So `gym.json` today is a one-shot, not cleanly a projection of stored docs. Three framings on the table (Dan is undecided):

1. **Docs→site projection (clean split).** Refactor: intake produces only knowledge docs (identity/brand/context/business); `generate` = the LLM step docs → `gym.json`. Makes `gym.json` a true re-runnable projection; becomes the engine that Phase 2 (AI editing) and `reskin` call. Cost: pull synthesis out of intake into generate.
2. **Thin-input generator (new capability).** `generate` builds a full site from minimal input (name, city, a few facts) for gyms we can't crawl / have no site. Sibling to intake, leaves it untouched. Ships fast; doesn't fix the docs/site blur.
3. **Reprojection engine (regenerate on demand).** `generate` re-runs docs → `gym.json` on demand (after doc edits, different archetype/template mix). Factors intake's synthesis into a reusable step both intake and the AI-editor call. Keeps intake as-is.

My lean (not decided): **#1 or #3** are the architecturally honest paths (both make synthesis a reusable docs→site projection; #1 also cleans up intake). #2 is a separate capability we can add anytime and doesn't resolve the core question. Recommend deciding #1 vs #3 first (mostly: do we refactor intake now, or just extract the reusable engine and leave intake as-is).
